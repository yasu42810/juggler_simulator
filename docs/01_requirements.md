## 1. 背景と目的

ジャグラーシリーズ（北電子のAタイプのパチスロ）は、設定1〜6でボーナス確率や小役確率がわずかに異なる。ホールにあるデータカウンタの値（総回転数・BIG回数・REG回数）と、自分で数えた小役の回数から、**台がどの設定である確率が何％か**をその場で求めたい。

本システムは、機種ごとの設定別確率データを事前に持ち、ユーザーが入力した実測値から **設定1〜6それぞれの事後確率** を計算して、グラフで示す。

### 1.1 ゴール

- G1: ホールでスマホを片手に持ったまま、台データ3項目を入力して結果を見るまで 30 秒以内（§7 の条件で測る）。
- G2: 結果の「不確かさ」が伝わる。数値だけでなく、各設定で想定される回数のばらつきと実測値の位置関係をグラフで見せる。
- G3: 代表1機種（マイジャグラーV）で作り込んだ後、他のジャグラーに横展開できる。**同じ判別要素の構造（BIG・REG・REG内訳・ぶどう）を持つ機種はデータファイル1つの追加だけ**、構造が違う機種（チェリーに設定差がある等）は計算モデルのモジュールを1つ追加するだけで対応でき、画面・保存・グラフのコードは変えない。
- G4: **打ちながら使える**。ぶどうやボーナスをタップで数え、回すにつれて推定がどう変わっていくか（事後確率の推移）を見られる。データが増えると多くの場合は推定が絞り込まれていくが、ボーナスの偏りで広がることもあり、それもそのまま見せる。

### 1.2 非ゴール（やらないこと）

- 設定を「確定」させること、勝てることを保証すること。
- ホールのデータサイトからの自動取得（スクレイピング）。
- ユーザー登録・サーバー側でのデータ保存。
- ジャグラーシリーズ以外（AT機・パチンコ）への対応。

## 2. 用語

| 用語 | 定義 |
|---|---|
| 設定 | 台の確率を決める段階値（1〜6）。高いほど出玉率が高い |
| 総回転数（G数） | データカウンタの総回転数。通常時のゲーム数で、ボーナス中のゲームは含まない（依頼者確認済み） |
| BIG / REG | ボーナスの種類 |
| 合算 | BIG と REG を合わせた確率 |
| ぶどう | 小役の一つ。設定差があるとされる。データカウンタには出ないため、自分で数える |
| 単独REG / チェリー重複REG | REG 当選時にチェリーが同時に成立したかどうかの内訳 |
| 公表値 / 解析値 / 実戦値 | データ種別。公表値=メーカーまたは市場調査値、解析値=第三者が調べた非公式の値、実戦値=実際に打った記録 |
| 事前分布 | 何も見ていない時点での、各設定である確率の想定。既定は「標準（低設定中心の想定）」（設定1〜6: 31.8/31.6/23.5/8.1/3.6/1.4%）。Web の情報を参考にした仮定。根拠は [research/setting-distribution.md](research/setting-distribution.md) |
| 事後確率 | 実測値を見たあとの、各設定である確率 |
| 遊技区間 | ユーザーが自分で打ち、小役を数えた区間。台データの区間に含まれる |
| 実戦モード | 打ちながら使うモード。打ち始めにカウンタの値を記録し、ぶどう・BIG・REG をタップで数え、カウンタの総回転数をときどき入れ直す |
| スナップショット | 実戦モードで総回転数を入れ直したときに記録する、その時点の入力一式。推移グラフの1点になる |
| 設定配分 | ホール（店）がその日に入れた設定の割合。将来、事前分布として使う |
| 未計測 / 0回 | 未計測=数えていない（空欄）。0回=数えたが出なかった。計算上の扱いが違う |

## 3. 利用者と利用シーン

### 3.1 利用者

- ジャグラーを打つ一般ユーザー（主に依頼者本人）。統計の専門知識は前提にしない。

### 3.2 利用シーン

| ID | シーン | 入力の例 |
|---|---|---|
| UC-1 | 台選び: 空き台のデータカウンタを見て、打つ候補を比べる | 総回転数, BIG, REG |
| UC-2 | 続行判断: 自分で打ちながら、ぶどうを数えて判断する | UC-1 + 遊技区間の回転数, ぶどう回数 |
| UC-3 | 振り返り: 帰宅後に結果を見直す | 保存した入力と推移 |
| UC-4 | 実戦: 打ちながらぶどう・ボーナスをタップで数え、推定が絞り込まれていくのを見ながら続行・ヤメを考える | 打ち始めのカウンタ値、タップ、ときどき総回転数 |

| FR-23 | 実測の BIG / REG / 合算 / ぶどう確率を「1/○○」で表示し、各設定の値と並べた表を出す | M |

| FR-25 | 分布グラフで表示する設定を切り替えられる（全設定 / 1設定を強調） | M |

| NFR-09 | プライバシー | 入力データは端末内（localStorage）にのみ保存する。アクセス解析は入れない |
| NFR-10 | 保守性 | 計算ロジックは画面から独立したモジュールにし、単体テストを持つ |

| NFR-12 | 権利 | メーカーのロゴ・筐体画像・キャラクターを使わない。公式と誤認される名称にしない。出典サイトの表・文章をそのまま転載しない |

## 6. 前提・制約

- C-01: 各ゲームの抽選は独立しており、確率は機種データの値で一定とする。ぶどうとボーナスは同じゲームで同時に当たらないとする。
- C-02: 入力したデータの区間内で設定変更はないとする。データカウンタの値は**その日の分**だけを使う（前日分を混ぜない）。
- C-03: 機種データは公表値・解析値であり、丸め誤差や解析の誤差を含む。特にぶどうは出典によって値が違い、結果に影響する。
- C-04: GitHub Pages を無料プランで使う場合、リポジトリは公開（public）にする必要がある（→ Q-08）。
- C-05: 事前分布の既定値は「標準（低設定中心の想定）」とする（依頼者要望: 設定6は入りづらいので傾斜をもたせる）。値は業界メディアの実データと Web 記事の推定を参考に決めた仮定で、特定の店の配分でも全国の実態でもない。事前分布で結果は大きく変わるため、前提として画面に出し、均等の場合の値も並べる（FR-17b）。その日の店の配分の推定は FR-32、店の傾向は FR-33（アイデア）で扱う。
- C-06: ぶどうは決められた規約（遊技区間の回転数はデータカウンタの差で数える、区間中は3枚掛けで揃ったぶどうをすべて数える、区間の境目を出方で決めない。→ Q-15）で数えた回数を入力してもらう。
