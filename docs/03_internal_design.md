## 4. 統計モデル（`juggler-standard-v1`）

### 4.1 前提と記号

前提: 各ゲームの抽選は独立で、確率は設定ごとに一定。1ゲームの抽選結果は「BIG」「REG」「ぶどう」「その他」のどれか1つ（ジャグラーでは、ぶどうとボーナスは同じゲームで同時に当たらないとされる）。

| 記号 | 意味 |
|---|---|
| s ∈ {1..6} | 設定 |
| π_s | 事前確率（既定は 1/6） |
| N, b, r | 台データの総回転数・BIG回数・REG回数 |
| r_a, r_c | REG のうち単独・チェリー重複と分類できた回数（不明分 = r − r_a − r_c） |
| n, g | 遊技区間の回転数・ぶどう回数（遊技区間は台データの区間に含まれる） |
| p^B_s, p^R_s, p^G_s | 設定 s の1ゲームあたりの BIG・REG・ぶどうの確率 |
| p^Ra_s, p^Rc_s | 単独REG・チェリー重複REG の確率（解析値） |

### 4.2 台データ（総回転数・BIG・REG）

各ゲームは「BIG」「REG」「それ以外」のどれか（多項分布）。

```
ln L_T(s) = b·ln p^B_s + r·ln p^R_s + (N − b − r)·ln(1 − p^B_s − p^R_s)
```

- 多項係数は設定によらないので省く。
- **合算は使わない**。BIG と REG から決まるので、尤度に掛けると同じ情報を二重に数える。
- BIG と REG を別々の二項分布として掛けるのは誤り（「それ以外」を二重に数える）。

### 4.3 遊技区間（ぶどう）— 条件付きの厳密な周辺化

遊技区間の中で何回ボーナスが当たったかは入力させない。それでも、§4.1 の前提（i.i.d.・排他）の下では次のように厳密に計算できる。ここで求めるのは「台全体の BIG・REG 回数が分かっているときの、遊技区間のぶどう回数の確率」`P(G_区間 = g | B = b, R = r, N, n, s)` であり、ぶどうだけを見た無条件の確率ではない。

1. 台データの区間 N ゲームのうち T = b + r ゲームがボーナス。各ゲームは独立・同じ確率なので、**ボーナスがどのゲームにあるかは N ゲームの中で一様にランダム**。よって遊技区間 n ゲームに入ったボーナス数 k は超幾何分布 `Hyp(k; N, T, n)` に従い、**これは設定によらない**。
2. 遊技区間のボーナス以外の n − k ゲームでは、ぶどうの確率は `q_s = p^G_s / (1 − p^B_s − p^R_s)`（p^G_s は対象ゲーム1回あたりの無条件の確率）。

```
L_P(s) = Σ_k Hyp(k; N, T, n) · Bin(g; n − k, q_s)
         k の範囲: max(0, n − (N − T)) ≤ k ≤ min(n, T, n − g)
ln w_s = ln π_s + ln L_T(s) + ln L_P(s)
```

- 対数空間で logSumExp を使って和を取る。k は最大でも 100 程度。
- この式は、遊技区間とそれ以外の区間を4カテゴリの多項分布で総当たりした計算（ブルートフォース）と一致することを確認済み（§9.3）。
- 参考: ぶどうを独立した二項分布 `Bin(g; n, p^G_s)` として掛ける近似との差は、試算した4ケース（N ≤ 8000）で事後確率の最大 0.44 ポイント。計算量はほぼ同じなので、近似ではなくこの式を採る。ただしこれは「上の前提を置いたモデルの中で厳密」という意味で、実際の入力が前提を満たさなければ近似になる（次項）。

#### この式が成り立つための条件

| 条件 | 内容 | 満たさないとき |
|---|---|---|
| 同じゲーム列 | N・n・機種データの確率が、同じ種類のゲームを数えている | 式の前提が崩れる。後述の計測規約で揃える |
| 区間の選び方 | 遊技区間の始まりと終わりを、ボーナスやぶどうの結果で決めていない | 例:「ボーナスが当たったらやめる」だと区間の最後が必ずボーナスになり、k の分布がずれる（1ゲーム分なので影響は小さい） |
| ぶどうの取りこぼし | 遊技区間で成立したぶどうをすべて数えている | ジャグラーのぶどうは取りこぼしがないとされる。目押しミス等で数え漏れがあると低設定寄りに偏る |

#### ぶどうの計測規約（依頼者了承済み: Q-15）

> 位置づけ: 以下は「入力をどう数えるか」の約束で、依頼者と合意済み。ただし、この数え方が機種データのぶどう確率の調べ方と同じであることは、どの出典にも書かれておらず**確認できていない**。§4.3 の式は「理想化した排他・i.i.d. のモデルの中で厳密」であり、実際の数え方とのずれは近似として残る。

N はデータカウンタの総回転数で、ボーナス当選ゲームや、当選後ボーナスを揃えるまでのゲーム（内部中）も含む。n も**同じ数え方**にそろえる。

- 遊技区間の回転数 n は、**区間の開始時と終了時のデータカウンタの総回転数の差**で求める（当選ゲーム・内部中のゲームを含む。ボーナス中は含まない）。ゲームを後から抜いたりしない。
- ぶどうは、その区間で揃ったものを**すべて**数える。区間中は3枚掛けで打つ（内部中に1枚掛けでぶどうを取る打ち方をすると、出方が変わるため）。
- 区間は「打ち始め」から「打ち終わり」まで。ボーナスやぶどうの出方を見て、区間の境目を決めない。
- 機種データのぶどう確率がどの条件で調べた値かを `measurement` に記録する。内部中のゲームでぶどうの出方が通常と違う場合、その影響（1日に数ゲーム程度）は近似として扱い、ヘルプに書く。条件が分からない出典の値は「解析値（条件不明）」と表示する。

#### 遊技区間のボーナス回数が分かる場合（実戦モード: Phase 1）

実戦モード（外部設計 §11）では、打ち始めのカウンタ値 (N0, b0, r0) と現在の値 (N, b, r) が分かるので、区間の回転数 n = N − N0、区間の BIG 回数 b_w = b − b0、REG 回数 r_w = r − r0 が分かる。また REG 内訳（§4.4, Phase 2）を使うと、区間で分類した REG の回数から r_w が分かる。この情報を使わずに上の式で k を周辺化すると厳密ではなくなるので、分かっている情報に応じて式を切り替える。

| 分かっているもの | ぶどうの尤度 |
|---|---|
| 区間内の b_w と r_w | `Bin(g; n − b_w − r_w, q_s)`（周辺化不要） |
| 区間内の r_w だけ | `Σ_j Hyp(j; N − r, b, n − r_w) · Bin(g; n − r_w − j, q_s)` |
| どちらも不明 | 上の `L_P(s)` |

- 台全体の回数が分かっているとき、区間内のボーナス回数の分かれ方は設定によらない（超幾何分布）ので、b_w・r_w そのものは設定の判別材料にならない。ぶどうの尤度の計算だけに使う。

### 4.4 REG 内訳（Phase 2）

「不明」は抽選のカテゴリではなく「分類できなかった」という観測の状態なので、多項分布のカテゴリにはしない。REG 総数は §4.2 で公表値を使って評価し、**分類できた REG の中の単独の割合**だけを追加の情報として掛ける。

```
θ_s = p^Ra_s / (p^Ra_s + p^Rc_s)        （REG のうち単独の割合）
ln L_S(s) = r_a·ln θ_s + r_c·ln(1 − θ_s)
```

- 前提: 分類できるかどうかは、単独か重複かに関係しない（例:「遊技区間のREGはすべて分類し、それ以外は不明」はよいが、「チェリーを見落としたときだけ不明になる」はよくない）。画面で「分類に自信がないものは不明にする」ではなく「自分で打った区間のREGだけ分類する」と案内する（Q-16）。
- 遊技区間の REG をすべて分類した場合は、区間内の REG 回数 r_w = r_a + r_c が分かる。このときのぶどうの尤度は §4.3 の「遊技区間のボーナス回数が分かる場合」の式を使う。
- 全件不明（r_a = r_c = 0）なら L_S = 1 で、内訳なしの結果と**完全に一致**する。内訳の ON/OFF で REG 総数の確率が変わることはない。
- REG 総確率は公表値のまま。内訳の解析値は割合 θ_s を作るためだけに使う。

### 4.5 指標の ON/OFF

- BIG と REG は常に使う（片方だけを外すとモデルが変わり、説明も難しくなるため）。
- 初版で切り替えられるのは **ぶどう**だけ（OFF なら L_P = 1）。Phase 2 で REG 内訳（OFF なら L_S = 1）を加える。
- ぶどうの入力が「未計測」（遊技区間の回転数かぶどう回数が空欄）のときは自動的に OFF と同じ扱い。「0回」は観測値として使う。

### 4.6 事後確率と集計値

```
P(s|D) = exp(ln w_s − M) / Σ_t exp(ln w_t − M)      （M = max_t ln w_t）
P(s≥4) = Σ_{s≥4} P(s|D)
機械割の事後加重平均 = Σ_s P(s|D) · 機械割_s
```

- 総回転数 0 なら事前分布がそのまま返る。事前確率が 0 の設定は事後確率も 0（`ln 0 = −∞` を特別扱いする）。
- すべての設定の重みが 0（`ln w_s = −∞`）になった場合は NaN を出さず、「この入力はモデル上起こり得ません」というエラーを返す。入力チェック（V-04: g ≤ min(n, N − b − r)）で通常は防げるが、計算側でも守る。
- 機械割の事後加重平均は「公表されている機械割を、推定した設定の確率で重み付けした参考値」であり、この先打ったときの収支を示すものではない。画面にもそう書く。
- 「設定4以上」などのまとめ方は機種データの `settingGroups` で決める（機種によって設定の段階が違っても対応できるように）。

**集中度**（推移グラフ用, FR-29）:

```
H(P)  = − Σ_s P(s|D)·ln P(s|D)            （エントロピー）
集中度 = 1 − H(P) / ln K                    （K = 設定の数。マイジャグラーV は 6）
```

- 事後確率が均等に散らばっていれば 0%、1つの設定に集まるほど 100% に近づく。事前分布によらない定義にする（偏った事前分布を使う将来も意味が変わらない）。
- **「正しい設定に近づいた」「当たりやすくなった」ことを示す値ではない**。ボーナスの偏りで下がることもある。画面とヘルプでそう説明し、「打つほど必ず精度が上がる」という表現は使わない。

### 4.7 モデルの部品化（横展開の方針）

依頼者の要望「他の台にも適用できる汎用性」に応えるため、**機種の違いを2段階で吸収する**。

| 機種の違い | 対応方法 | 変更するもの |
|---|---|---|
| 確率の値だけが違う（例: アイムジャグラーEX、ファンキージャグラー2 が v1 の構造に収まる場合） | 機種データ（JSON）を1つ追加 | データとそのテストだけ |
| 判別要素や抽選の関係が違う（例: チェリーに設定差がある、ボーナスの種類が違う） | 計算モデルのモジュールを1つ追加し、`SettingModel` を実装 | モデルとそのテストだけ。画面・保存・グラフは変えない（ただし下の「共通の画面契約」で表せる範囲に限る） |

**共通の画面契約で表せる範囲**: 入力は「台全体のゲーム数と回数」「自分の区間のゲーム数と回数」の2層で、各項目は 0 以上の整数の回数。実戦モードでは、台全体の回数の増分がそのまま区間の回数になる項目（ボーナス）と、区間だけで数える項目（小役）の2種類。これに収まらない機種（例: ゲーム数以外の入力が要る、区間が3層以上）は、画面側の対応も含めて新しい要件として扱う。

#### SettingModel インターフェース

画面・保存・グラフは、モデルが宣言した内容だけを見て動く。

```ts
// src/core/models/types.ts
interface FieldDef {
  key: string;                    // 例: "big", "grape"
  label: string;                  // 例: "BIG", "ぶどう"
  kind: "count";                  // 現在は 0 以上の整数の回数だけ（将来の拡張用）
  scope: "total" | "session";     // total: カウンタで見える回数 / session: 区間だけで数える回数
  // total の項目は、実戦モードで「台全体の増分 = 区間の回数」として扱う（ボーナス）
  counterButton: boolean;         // 実戦モードで +1 ボタンにするか
  optional: boolean;              // 空欄（未計測）を許すか
  max?: number;                   // 入力上限（目安）
  measurementNote?: string;       // 入力欄の近くに出す数え方の説明
}

interface ModelCapabilities {
  playMode: boolean;              // 実戦モードに対応するか（対応しないモデルはかんたん入力だけ）
  sessionBonusKnown: boolean;     // 区間のボーナス回数が分かると尤度の式が変わるか（§4.3）
}

interface Observation {           // モデル共通の、検証済みの入力（observation.ts だけが作る）
  total:   { games: number; counts: Record<string, number> };
  session: null | {
    games: number;
    counts: Record<string, number | null>;   // 区間だけで数える回数（null = 未計測）
    totalDelta: Record<string, number> | null; // 区間の total 項目の回数（実戦モードなら current − start、分からなければ null）
  };
}

interface SettingModel<M extends MachineDataBase> {
  id: string;                                        // "juggler-standard-v1"
  version: string;                                   // モデルの版（計算方法を変えたら上げる）
  capabilities: ModelCapabilities;
  parseMachine(json: unknown): M;                    // 機種データの検証（D-xx）。不正なら例外
  fields(machine: M): FieldDef[];
  toggles(machine: M): { key: string; label: string }[];   // ON/OFF できる判別要素
  validate(machine: M, obs: Observation): Issue[];   // 入力チェック（V-xx）
  logLikelihood(machine: M, obs: Observation, setting: string,
                opts: { enabled: Record<string, boolean> }): number;
  charts(machine: M, obs: Observation): ChartData[]; // 分布グラフのデータ（§4.8）。描画はしない
  compareRows(machine: M, obs: Observation): CompareRow[];  // 比較表のデータ
}

// モデルが返すのは型付きのデータだけ。UI 部品は返さない（モデルを画面なしでテストできるように）
interface ChartData { id: string; label: string; note?: string;
                      series: { setting: string; points: { k: number; p: number }[] }[];
                      observed: number | null; secondaryAxis?: "oneIn" }
interface CompareRow { label: string; observedOneIn: number | null;
                       bySetting: Record<string, number>; dataType: DataType }
```

- 事後確率の計算（`posterior.ts`）は `logLikelihood` を設定ごとに呼ぶだけで、モデルの中身を知らない。これにより、設定ごとの**尤度ベクトル**を事前分布と切り離して扱える（§4.10 の設定配分の推定でもそのまま使える）。
- `juggler-standard-v1` が扱うのは BIG・REG・REG内訳・ぶどう。チェリーなどを追加する機種は、チェリーとチェリー重複REGの重なりなど抽選の関係が変わるため、別モデル（例: `juggler-cherry-v1`）として作る。共通の計算（多項分布・超幾何の周辺化）は `core/math.ts` の関数として再利用する。
- 未知の `model` を持つ機種データや、モデルが知らない項目を持つ機種データは、読み込み時に拒否する（暗黙に無視しない）。
- 生の入力（かんたん入力の文字列、実戦記録）から `Observation` への変換は `observation.ts` の1か所だけで行う。区間の total 項目の回数（`totalDelta`）は、実戦モードでは常に `current − start` から計算し、別に保存しない（同じ値を2か所に持たない）。
- 画面が本当にモデルに依存していないことを、テスト用のダミーモデルで確かめる（受け入れ基準 A-18）。ダミーモデルは**項目の数・種類が違い、実戦モードに対応しない**ものにする（名前だけ変えたモデルでは確かめたことにならない）。

### 4.8 分布グラフ（FR-24）

```
P(K = k | s) = C(m, k) · p^k · (1 − p)^(m − k)       （二項分布）
```

| タブ | m | p |
|---|---|---|
| BIG | N | p^B_s |
| REG | N | p^R_s |
| 合算 | N | p^B_s + p^R_s |
| ぶどう | n | §4.3 のぶどうの尤度と同じ式（台の BIG・REG 回数を条件にした分布） |

- BIG・REG・合算は、§4.2 の多項分布から1つの指標だけを見た分布（周辺分布）で、二項分布として正確。
- ぶどうは、事後確率の計算と同じ §4.3 の式で描く。BIG・REG タブ（無条件の二項分布）とは意味が違い、「台の BIG・REG 回数を踏まえたときの、遊技区間のぶどう回数の分布」であることをグラフの注記に書く。計算量は 6設定 × 数百点 × 最大 100 項で、N=20,000 を含めて §7 の予算内であることを性能テストで確かめる。
- 入力チェック V-07（ぶどうが起こりにくい値か）もこの分布で判定する。判定は「全設定で、P(K ≤ g) < 0.1% または P(K ≥ g) < 0.1%」（片側ずつ 0.1%）。
- 対数で計算する: `lnC(m,k) + k·ln p + (m−k)·log1p(−p)`。`lnC` は ln(k!) の表（0〜20,000 を初回に作って使い回す）から求める。
- **表示範囲**: 6設定それぞれの 0.1% 点〜99.9% 点の和集合に、実測値を加えた範囲（実測値が必ず入る）。点の数は最大でも数百。表示範囲の外の確率を足して再正規化はしない。
- 期待回数が小さい（例: 5回未満）ときは釣鐘形にならないので、点を線で結ばず棒で描く。
- m = 0 のときはグラフを出さない（「回転数を入れると表示されます」）。実測 0 回のときは「1/○○」換算を出さない。

### 4.9 データの不確かさ（感度）

- 公表値の丸め（例: 1/273.1）による誤差は、1日分の回転数では結果にほぼ影響しない。
- ぶどうの解析値は出典によって設定間の差の形自体が違う（[調査メモ §4](research/my-juggler-v-spec.md)）。例: N=3000, B=12, R=11, n=1500, g=265 で、採用候補（設定1〜6: 5.90/5.85/5.80/5.78/5.76/5.66）だと設定4以上 64.4%、別出典の逆算値（5.90/5.87/5.84/5.84/5.84/5.81）だと 63.1%。
- 対策:
  - 調査メモに候補のデータ一式をすべて残し、採用理由を書く（Q-03）。
  - `tests/sensitivity` で候補データ一式ごとに入力の格子（N・b・r・n・g）を計算し、事後確率の最大差を記録する。差が大きい入力範囲を把握してヘルプに書く。
  - 画面でぶどうの値が「解析値」であることを示し、ぶどうを計算から外せるようにする（§4.5）。

## 5. 機種データ設計

### 5.1 方針

- 1機種 = 1 JSON ファイル（`src/machines/data/<id>.json`）。`registry.ts` が `import.meta.glob` で読み込む。本番ビルドでは `status: "active"` の機種だけを機種一覧に出す。
- 確率は出典の表記どおり「1/x」で持つ（`{"oneIn": 273.1}`）。内部抽選値が分かる場合は `{"num": 100, "den": 65536}` でも書ける。
- 合算は持たない（BIG・REG から計算）。照合用の公表値は `published` に入れ、テストで計算値と比べる。
- 値の表ごとに **データ種別**（公表値/解析値/実戦値）、**出典**、**採用理由**、**計測条件** を持つ。分からない値は書かない（0 を入れない）。
- 後継機・同スペック機（例: マイジャグラーⅥ）は別の機種として別ファイルにする。`aliases` は表記揺れ（「マイジャグ5」など）にだけ使う。

### 5.2 型定義

機種データは「全モデル共通の部分（`MachineDataBase`）」と「モデルごとの部分」に分ける。画面・保存・事前分布は共通部分だけを見る。

```ts

type DataType = "published" | "analysis" | "measured";  // 公表値 / 解析値 / 実戦値

interface MachineDataBase {
  schemaVersion: 1;
  model: string;              // 例: "juggler-standard-v1"。対応するモデルが読み込む
  id: string;                 // URL にも使う（kebab-case）
  name: string;
  maker: string;
  releaseDate?: string;       // YYYY-MM-DD
  aliases?: string[];         // 表記揺れのみ
  dataVersion: string;        // YYYY-MM-DD
  status: "active" | "draft";
  settings: string[];         // 例: ["1","2","3","4","5","6"]。機種によって段階が違っても対応
  settingGroups: { label: string; settings: string[] }[];  // 例: 設定4以上, 設定5以上, 設定6
  payout: {
    values: Record<string, number>;  // 設定 → %
    condition: string;        // 例: "公式出玉率（工場データからの予測値）"
    dataType: DataType;
    sourceIds: string[];
  };
  priorPresets?: { id: string; label: string; weights: Record<string, number> }[];
  sources: { id: string; title: string; url: string; accessed: string }[];
}

// juggler-standard-v1 固有
interface ProbTable {
  values: Record<string, ProbValue>;   // 設定 → 確率
  dataType: DataType;
  measurement: string;        // 例: "通常時ゲーム数あたり"
  sourceIds: string[];
  basis?: string;             // 採用理由（複数の候補から選んだ理由など）
}

interface JugglerStandardV1Data extends MachineDataBase {

    big: ProbTable;
    reg: ProbTable;
    regSolo?: ProbTable;      // regSolo と regCherry は両方あるか両方ないか

    grape?: ProbTable;
  };
  published?: { combinedOneIn?: Record<string, number> };
}
```

## 6. 状態管理と保存

### 6.1 状態

```ts
// state/store.ts
const machineId   = signal<string>("my-juggler-v");
const input       = signal<RawInput>(emptyInput);  // 文字列のまま保持（入力途中の値を壊さない）
const priorChoice = signal<PriorChoice>({ type: "uniform" });
const useGrape    = signal<boolean>(true);
const context     = computed(() => ({ machineId, dataVersion, prior, useGrape }));  // 結果の前提
const parsed      = computed(() => validate(machine.value, input.value));
const result      = computed(() => parsed.value.ok
  ? estimate(...)                                   // 前提（context）を結果に含める
  : sameContext(lastGood, context) ? stale(lastGood) : null);
```

- 入力エラーのとき、前回の結果は**前提（機種・データ版・事前分布・ぶどう ON/OFF・REG内訳 ON/OFF）が同じ場合だけ**薄く残し、「前回の有効な入力（N=○, BIG=○, …）での結果」と、その入力を添えて表示する。前提が変わったら消す。

### 6.2 localStorage

| キー | 内容 |
|---|---|
| `jsim:v1:prefs` | 選択中の機種、表示設定、事前分布、ぶどうON/OFF |
| `jsim:v1:input:<machineId>` | 機種ごとの入力値と最終更新日時 |
| `jsim:v1:slots` | 複数台の保存（Phase 2） |

### 6.3 実戦モードの記録（playSession.ts）

```ts
interface PlaySession {
  version: 1;
  id: string;                    // UUID
  machineId: string;
  // 計算の前提を開始時に固定する（後でデータやモデルが更新されても、当時の結果を説明できるように）
  conditions: { modelId: string; modelVersion: string; dataVersion: string;
                prior: { id: string; version: string; weights: Record<string, number> };  // 名前だけでなく実際の重みも保存
                enabled: Record<string, boolean> };
  startedAt: string;             // ISO 日時
  endedAt?: string;
  start:   { games: number; counts: Record<string, number> };  // 打ち始めのカウンタ値（BIG, REG）
  current: { games: number; counts: Record<string, number> };  // ★正本: 最新の台全体の値
  sessionCounts: Record<string, number>;                       // ★正本: 区間だけで数える回数（ぶどう）
  undo: UndoEntry[];             // 直前の状態（最大 200 件。古いものから捨てる）
  snapshots: { t: string; games: number; counts: Record<string, number>;
               sessionCounts: Record<string, number>;
               posterior: Record<string, number> }[];   // その時点の値と、当時の条件での事後確率
  memo?: string;                 // 台番号など
  hall?: string;                 // 店名（任意。Phase 4 の設定配分で使う）
}
// 戻す用の差分。全体を複製せず、スナップショットは「件数」と「直前の最後の点」だけを持つ
type UndoEntry = { op: "inc" | "snapshot"; label: string;
                   prev: { current: Counter; sessionCounts: Record<string, number>;
                           snapshotCount: number; lastSnapshot: Snapshot | null } };
```

**正本と導出の規則**

- 台全体の値は `current`、区間だけで数える値は `sessionCounts` が正本。区間の BIG・REG 回数・区間の回転数は常に `current − start` から計算し、別には持たない。
- BIG/REG のボタンは `current.counts` を +1 する（区間の回数は差分から自動的に +1 になる）。

**操作の種類**

| 操作 | 内容 | 戻す |
|---|---|---|
| inc | ぶどう・BIG・REG の +1 | 直前の値に戻す |
| snapshot | 総回転数の更新。ダイアログで N・BIG・REG を確定し、`current` を置き換えて、スナップショットを追加する。N が前回と同じなら最新のスナップショットを**置き換える** | 確定前の `current` と、スナップショット件数に戻す |
| （訂正） | 実装では snapshot に含めた。総回転数の更新ダイアログで BIG・REG・ぶどうを減らす訂正ができ、警告を出してから確定する。残る直前の点より回数が減った点には `corrected: true` を付け、推移グラフに注記する（同じ回転数で置き換えた場合は、誤った点が消えるので付けない） | 訂正前に戻す |
| （打ち始めの訂正） | Phase 1 では未実装。打ち始めの値を間違えたときは、記録を破棄してやり直す | — |

- 戻すときは、`UndoEntry.prev` の状態に戻す（台全体・区間・スナップショットがそろって戻る）。戻せるのは直近 200 操作まで。打ち終わると戻す履歴は捨てる。
- 打ち始めと同じ総回転数での更新は V-10 で拒否する（打ち始めの点は置き換えない）。
- 終了した記録への操作は `EndedSessionError` で拒否する。
- 総回転数の更新ダイアログを開いている間は、カウンターボタンを押せないようにする（確定する値が途中で変わらないように）。

**入力チェック（実戦モード）**: 外部設計 V-10, V-11 に加えて、区間について

```
n = current.games − start.games ≥ 0
0 ≤ b_w + r_w ≤ n          （b_w = current.big − start.big, r_w = current.reg − start.reg）
0 ≤ g ≤ n − b_w − r_w
```

を満たさなければ、スナップショットを確定しない（V-12）。

**数値の基本検証**: どの経路（かんたん入力・実戦モード）から来た入力も、モデルの `validate` の最初に `numericIssues`（0以上の整数・上限 100,000 以下）で確かめる。画面側の検証だけに頼らない。

**機種データ・モデルの版が変わった後の再開**: 記録の `conditions` と今の機種データ・モデルの版が違う場合、カウンターを止めて「新しいデータで続ける」か「終了して履歴に残す」を選んでもらう。続ける場合は `conditionChanges` に変更した時点（総回転数）と版を記録し、それまでの点は記録当時の結果のまま残す。古い版の機種データは保持しないので、古い条件で計算し直すことはしない。

**推移の再計算**

- 推移グラフは、スナップショットに保存した**当時の事後確率**を描く。機種データ・モデル・事前分布が更新された後に開いた場合は「当時の条件での結果」と表示し、「今の条件で再計算」ボタンで再計算した推移も見られるようにする（区別して表示する）。
- 事後確率はスナップショットの値だけで計算する（最新のタップ数と古い回転数を混ぜない。外部設計 §11.2）。

**保存**

- localStorage のキー: `jsim:v1:play:active`（進行中の1件）、`jsim:v1:play:history`（終了した記録。最大30件）。タップのたびに保存する。
- 容量の目安: 進行中の記録は undo 200件で数十KB 程度。終了時に `undo` を捨て、スナップショットだけを履歴に残す（1件数KB、30件で 100KB 程度）。実装時に実データ量で書き込み時間を測る。
- 保存に失敗したら（容量超過など）すぐに画面に出し、古い履歴を消すかどうかを聞く。

## 7. 性能

- 事後確率: 6設定 × 超幾何の和（最大 100 項程度）。1ms 未満の見込み。N=20,000・ボーナス 150 回のような重い入力でも測る。
- 分布グラフ: 6設定 × 数百点。ln(k!) の表（20,001 要素, 約160KB のメモリ）を初回だけ作る。
- 入力は1文字ごとに再計算してよい。グラフの再描画は `requestAnimationFrame` でまとめる。
- バンドル予算: gzip 後 200KB 以下（Preact 約 4KB、Chart.js 必要部品のみ 約 60KB）。CI でサイズを確認する。

#### その日の店の配分の推定（FR-32。次に着手する機能の設計方針）

依頼者の「ホール全体での設定の入り方を参考にした事後分布」の要望に向けた方針。**設定は日ごとに入れ替わるので、推定に使うのはその日のデータだけ**とする（依頼者の判断。複数日を合算すると、その日の配分が薄まる）。

- **モデル（階層ベイズ）**: ある店・**ある日**の設定配分を α = (α_1..α_6) とし、各台 i の設定 s_i は α に従って独立に決まるとする。α には事前分布 Dirichlet(β) を置く（β は「店の傾向が分からない」ときの弱い想定）。
- **使うデータ**: 同じ店・同じ日の複数台について、各台のモデルの尤度ベクトル L_i(s)（§4.7 の `logLikelihood` をそのまま使う）。データカウンタの値（総回転数・BIG・REG）を台ごとに入れてもらう。
- **台の単位**: 1台・1営業日（設定が変わらない区間）につき**尤度は1つだけ**。同じ台の複数のスナップショットや、同じ台を2回入れたものは、最新の累計で置き換える（重複排除。そうしないと同じ観測を二重に数える）。
- **計算**: α の事後分布は `p(α | D) ∝ Dir(α; β) · Π_i Σ_s α_s L_i(s)`。次のどちらで計算するかを決めて明記する。
  - 完全ベイズ: ギブスサンプリングで α の事後分布を求める（不確かさまで反映される）。
  - 経験ベイズ（近似）: EM で α の点推定を求めて事前分布にする（簡単だが、台数が少ないと過信しやすい）。
  - 推奨は完全ベイズ。6次元なので端末内で十分速い見込み。
- **使い方**: 調べたい台 j の事前分布として、**台 j 自身を除いた**他の台から推定した `E[α | D_{−j}]` を使う。この場合 `P(s_j = s | D) ∝ L_j(s) · E[α_s | D_{−j}]` がモデルの下で正確に成り立つ。成り立つ条件は、β を固定していること、全台で設定の段階が同じこと、α が決まれば台どうしの設定は独立であること。
- **拡張口**: `PriorProvider` の `hallEstimate` として実装し、事後確率の計算・画面のコードは変えない。台データの入力は `PlaySession` / 複数台保存（FR-40）の `hall`・日付を使ってまとめる。
- **注意**:
  - 店の設定の入れ方は台ごとに独立とは限らない（並び・末尾・機種ごとの傾向など）。初めは「独立」とし、拡張は要件化してから検討する。
  - **どの台のデータを集めるか**で結果が偏る。自分が選んだ台・よく回っている台だけから推定すると、店全体の配分とは一致しない。対象（例: その日のその機種の全台）と集め方を決め、偏りのある集め方ならそう表示する。
  - 設定の段階が違う機種を、同じ α にそのまま入れない。機種・島ごとにどこまで同じ α とみなすかも、この機能の要件で決める。
  - **推定の幅について**（2026-10-25 に、ある店の1日分・23台・各5,000G前後で試算）: 「設定4以上の割合」は 90% 区間で 22〜66% と、ある程度見える。一方で設定ごとの割合は、どれも 90% 区間が 1〜45% 程度と広く、ほとんど決まらない。原因は日数ではなく**1台あたりの情報の少なさ**（ジャグラーは設定差が小さく、5,000G では1台ごとに設定3か4かをほぼ見分けられない）。画面では設定ごとの割合だけでなく、「設定4以上の割合」とその幅を主に見せる。幅を狭めるには、閉店時のデータ（1台あたりの回転数が多い）を使う、同じ日の他のジャグラー機種も入れる、などが効く。

#### その日の店の配分の推定: 実装メモ（Phase 2.5）

- `src/core/priors/hallEstimate.ts`: ギブスサンプリング（既定 4,000 回、捨てる初期分 500 回、seed 固定で再現可能）。α の事前分布は Dirichlet(1,…,1)（店の傾向が分からない想定）。事前分布として使う平均は、各回の条件付き期待値 (β + 台数) / (Σβ + 台数合計) の平均（Rao–Blackwell 化）で求める。台数が少ないときは、全パターンの数え上げによる厳密な値とテストで照合している。
- `src/state/hallData.ts`: ファイル（JSON）の読み込み。形式は `{ source: {hall, machine}, fetchedAt, rows: [{unit, totalGames, big, reg, ...}] }`。不正な行・重複した台は読み飛ばし、理由を表示する。機種名が違えば警告する。データは端末の localStorage（`jsim:v1:hall:<機種ID>`）にだけ保存する。
- 見たい台は「この台を見る」で選ぶ。選んだ台を除いた推定が事前分布になり、かんたん入力にその台の値が入る。入力が一覧の未選択の台と同じ値なら、その台を選ぶよう警告する（同じデータを推定と入力の両方に使わないため）。
- 事前分布の選択肢に「店のその日のデータから推定」が加わる。前提表示には日付・台数・除いた台番号を出す。

#### 店の傾向の推定（FR-33。アイデアとして残す）

- **目的**: その日のデータが少ないとき（朝など）や、データのない日の予想に使う出発点。その日のデータが増えるほど、その日の推定に寄っていく。
- **モデル**: 店 → 日 → 台 の3段の階層。日ごとの配分 α_d は、店の傾向 μ を中心に `α_d ~ Dirichlet(κ·μ)` でばらつくとする（κ は日ごとのばらつきの小ささ）。通常日とイベント日（特定日）は別の μ を持たせる。
- **やらないこと**: 複数日のデータを単純に合算すること（その日の配分ではなく「平均的な日」の配分になり、日ごとの違いが消える）。
- **データの集め方の注意**: 店のデータサイトは規約で情報の収集を禁止している場合がある。過去の日のデータを集める方法は、規約を確認したうえで依頼者が判断する。

#### 店に入っている複数のジャグラー機種をまとめて見る（FR-34。アイデアとして残す）

依頼者のアイデア（2026-10-25）: ジャグラーは機種ごとに設定別の確率や機械割が違うので、今の仕様では1機種ずつしか値を出せない。何らかの形で正規化して、店に入っている全ジャグラーをまとめた値を出したい。

- **正規化の考え方**: 確率や回数そのものをそろえる（例: 「設定1と設定6の間のどこにいるか」に換算して平均する）のではなく、**各台のデータを、その台の機種のモデルで評価して「設定1〜6それぞれの尤度」にする**。設定の番号（1〜6）は機種をまたいで共通なので、尤度にした時点で機種の違いは吸収される。FR-32 の推定（`estimateHallMix`）は台ごとの尤度ベクトルしか使わないので、機種の違う台をそのまま同じ推定に入れられる。
  - 回転数が多い台・設定差の大きい機種の台ほど尤度の差がはっきりするので、推定への効き方も自然に重み付けされる（単純な平均では、この重みが付かない）。
- **機種ごとの扱いの違い**: 店によっては機種ごとに設定の入れ方が違う（例: ある機種は高設定を多めに使い、別の機種は回収寄り）。そこで2つの段階を用意する。
  1. 全機種で同じ配分 α を使う（台数が少ないときはこちら）。
  2. 機種ごとの配分 α_m が、店全体の配分 α_店 のまわりでばらつくとする（`α_m ~ Dirichlet(κ·α_店)`、部分的なプーリング）。機種ごとの傾向と店全体の傾向を同時に推定できる。κ が大きいほど「機種による違いは小さい」という想定になる。
- **結果の見せ方（機種によらない共通の物差し）**:
  - 店全体の「設定4以上の割合」とその幅。
  - 店全体の機械割の見込み: 各台について Σ_s P(s | データ)·機械割_機種(s) を求め、回転数で重み付けして平均する。同じ「設定6」でも機種によって機械割が違う（例: マイジャグラーV は 109.4%）ので、設定の割合よりも「どれだけ出しているか」を直接比べられる。
  - 機種ごとの推定を並べて、どの機種に高設定が多そうかを見る。
- **前提・必要なもの**:
